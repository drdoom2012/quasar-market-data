# FR-3 Funding Rate Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Binance USDT-M funding rate history source on its **own** CCXT client with the request rules of ADR-0004 P-5, a local limiter (305 s window, class caps), `429`/`418` handling through one shared `ExtensionPause`, and the `fetch-funding-once` command (issue #18).

**Architecture:** Three small collector modules and one orchestration module, mirroring the open interest ones (OI-3): `extension_pause.py` (the object P-9 names), `funding_rate_limiter.py` (the sliding window with class caps R and C+H, and the in-flight slots), `binance_usdm_funding_rate.py` (the adapter: pause check → limiter grant, which holds an in-flight slot → pause check → raw `fapiPublicGetFundingRate`), `fetch_funding_rate_once.py` (server time → range → raw page → FR-1 parser → FR-1 eligibility → FR-2 writer without a `merge`). The CLI wires them. No scheduler, no task, no config table (FR-4).

**Tech Stack:** Python 3.12, CCXT 4.5.89 async (`binanceusdm`, implicit endpoint `fapiPublicGetFundingRate`), asyncio, pytest, mypy strict, ruff, import-linter.

**Spec:** `docs/adr/0004-funding-rate.md` (P-1, P-3, P-4, P-5, P-9, P-15 rows marked FR-3 or FR-3/FR-4, P-16), FR-1 (`domain/funding_rate.py`, `domain/funding_rate_capacity.py`, `collector/binance_funding_rate.py`), FR-2 (`collector/async_funding_rate_writer.py`). Pattern to mirror: `collector/binance_usdm_open_interest.py`, `open_interest_gate.py`, `open_interest_budget.py`, `fetch_open_interest_once.py`, `tests/collector/test_binance_usdm_open_interest.py`, `test_open_interest_gate.py`, `test_open_interest_budget.py`, `test_fetch_open_interest_once.py`, `test_cli_fetch_oi_once.py`, `docs/superpowers/plans/2026-11-02-oi-3-open-interest-adapter.md`.

## Decisions this plan makes (not fixed by the ADR)

- **`ExtensionPause` is the object P-9 names and is a new class, not the open interest gate renamed.** It has the same semantics as `OpenInterestGate` (429: pause `max(Retry-After, min(300 s · 2^(n−1), 1 h))`, a success after the pause resets the doubling, a `Retry-After` above one hour is honoured; 418: stop for the process run; a request in flight when a 429 arrived cannot reset the doubling; `check()` raises at once instead of waiting), but it exposes the two facts P-9 lists (`paused_until`, `stopped`) and is dataset-neutral (`ExtensionPaused`, `ExtensionStopped`, both `SourceError`). The open interest task keeps its own gate until amendment A-3 (#21) moves it onto this class; FR-3 does not edit open interest.
- **The limiter is a new class, `FundingRateLimiter`, not the FIFO `OpenInterestBudget`, and it owns the in-flight slots.** P-9 needs the 305 s left-open window (a start at `s` counts while `t − 305 s < s`) and two class caps that are never lent: R ≤ `m = floor(b / 2)`, C and H together ≤ `b − m`. `RequestClass` (members `R`, `C`, `H`; C and H share the second cap, their alternation is the FR-4 scheduler's rule) lives in `domain/funding_rate_capacity.py` because the FR-4 scheduler is a pure function; the limiter re-exports it. Each cap group has its own FIFO lock, so a saturated group never blocks the other. **The slot is taken after the room is known and before the start is recorded** (review finding 2): a request holds its group lock while it waits for room, then takes one of the `MAX_IN_FLIGHT = 2` slots (still holding the group lock, so the room cannot shrink), records the start, releases the group lock and keeps the slot until the call ends. Waiting for room therefore never holds a slot (a saturated R group cannot block C/H, nor the reverse), and the start is recorded at the instant the slot is held, so the sends of a group are at least 305 s apart in the same sense as the grants. The offered API is the async context manager `async with limiter.grant(request_class): ...`. `b` is validated with the FR-1 `round_share` / `history_catchup_share` (50..250). The sleep and clock are injected. The "deadline" of P-15 ("exhausted budget and an expired deadline drops the request unsent") is the caller's `asyncio.timeout`: a request cancelled while it waits records no start, takes no slot and sends nothing (tested in Task 2 and Task 3).
- **The adapter's request methods take the class.** `fetch_server_time(request_class=RequestClass.R)` and `fetch_funding_rate_history(symbol, start_time_ms, end_time_ms, *, request_class)`. The server-time call and seed/round requests are R (P-9); catch-up is C, history H. FR-3 only passes them through to the limiter.
- **Public CLI behaviour that is new (for the user to see with this plan):** the subcommand `fetch-funding-once`, its flags `--db`, `--symbol`, `--hours` (1..500, default 24), `--publication-delay-ms` (0..595 000, default 30 000), its output lines and its exit codes, and the refusal of an inactive market (below). `fetch-funding-once` is named in the accepted ADR-0004 P-16.
- **Request validation is in the adapter, before any pause check, grant or network use**, with this mapping: a bound that is not an `int` (or is a `bool`) → `TypeError` (a caller bug, as `ensure_timestamp_ms`); a bound outside the timestamp range or `start > end` (Binance answers `200 []` for the reverse, P-5 rule 5, which would read as an empty answer) → `FundingRateRequestRefused(SourceError)`; a symbol that is unknown, not a USDT-margined linear perpetual (`usdm_market_id`) **or not active** (`markets[symbol].get("active") is True`) → `FundingRateRequestRefused` wrapping the cause. P-5 requires an *active* market so that a delisted contract never reaches `200 []`; `usdm_market_id` (shared with the candle path, unchanged) does not check `active`, so the funding adapter adds the check (134 of 882 markets in the repository's fixture are not active). `limit` is always `FUNDING_RATE_PAGE_LIMIT` and `startTime` is always sent.
- **The response is returned untouched** (a `list`; anything else is a `SourceError`, as the OI adapter) for the FR-1 parser. The adapter does not parse.
- **CCXT retry check (P-9 [P]), verified for CCXT 4.5.89:** `fetch2` loops `maxRetriesOnFailure + 1` times and retries only `OperationFailed` (which includes `RequestTimeout`, `DDoSProtection` and `RateLimitExceeded`); the option is read from the request params, `options['fundingRate']`, and `options['defaultMaxRetriesOnFailure']`, default 0. Tests: a stubbed transport (`fetch`) raising a timeout and a 429 sees exactly one call each (a real `ccxt.async_support.binanceusdm()` with markets stubbed, no network); the client has none of the three settings and the adapter's params carry no such key. The result is recorded in the module docstring and the PR; the ADR evidence text is **not** edited (it needs approval).
- **A real CCXT never returns the HTTP-200 error object as a dict:** `handle_errors` raises `BadRequest` for `-1130`. The adapter still rejects a non-list response (a fake or a future CCXT), and `test_1130_is_an_ordinary_source_error` pins the real path.
- **`fetch-funding-once` stores rows and claims no coverage.** It never calls `merge`: a row outside or inside the span claims nothing (P-7). It observes server time on the funding source, evaluates the lower bound before the history call (conservative: the source's waits can only make it older), and requests **one** page of class R over `[end − hours·1h, end]` with `end = forward_end_bound_ms(delay, lower_bound)` (FR-1), so the width is exactly `hours` hours and `start ≤ end` always. It parses all-or-nothing, selects eligible rows (FR-1) and writes them through the FR-2 async writer. `--hours` is 1..500 (default 24); `--publication-delay-ms` is 0..595 000 (P-12: `round_offset_ms ≤ 600 000` and at least `delay + 5 000`), validated in the config. A full page (`n == 1000`) is reported as `full_page=true` and is still valid (the command never says the range is complete). With untrusted time no request is made (as OI-3), exit `1`. Because the end bound equals `lower_bound − delay` and the parser rejects any later row, `selection.pending` cannot be non-empty; if it ever is, the command fails closed before any write with `FundingRateSelectionError(SourceError)` (exit `1`). Exit codes otherwise as `fetch-oi-once` (`0`, `3` on conflicts, `1`, `4` for an unknown or partial write, `130`, `2`).
- **The command prints** `symbol=… start_ms=… end_ms=… fetched=…`, `time=trusted|untrusted reason=…`, `inserted=… duplicates=… conflicts=… pending=… off_hour_rows=… full_page=true|false`. The off-hour count is FR-1's heuristic: counted, never a rejection, and (P-3) **logged at warning level**: when `off_hour_rows > 0` the command writes one stderr line `warning: N off-hour row(s) (fundingTime more than 5 s after a whole hour); stored`.
- **`budget_per_5min` for the command is the default 150** (`DEFAULT_BUDGET_PER_5MIN` from `domain/funding_rate_capacity`, imported in `cli.py` **with an alias** `DEFAULT_FUNDING_BUDGET_PER_5MIN`, because `cli.py` already imports the open interest `DEFAULT_BUDGET_PER_5MIN` = 400, which `FundingRateLimiter` would refuse); the configuration key is FR-4. A fresh limiter has an empty window, so it never delays a one-shot command.
- **README states the operational requirement** (nothing else on the IP may call `fundingRate` or `fundingInfo` more than `500 − b` times per 5 minutes) and names the new command; the output lines and exit codes go into `docs/reference.md`, as for the other commands, together with one paragraph on the modules.
- **Paging (P-15 Paging row, FR-1/FR-3):** FR-1 owns `page_coverage`; FR-3 adds one adapter-level test that drives it over the fake source (999, 1 000, 1 000 with a shared final `fundingTime`, 2 500 rows) to show that the requests the source accepts are the ones the rule produces (the next request starts at `last`, every request has `limit=1000`).

## Review Focus

1. A stream that saturates both groups at `b = 50, 150, 250` (odd `b` too) never starts more than `b` requests in any 305 s interval; request `k + b` starts at exactly `305 000 ms` after request `k` (not `304 999`); R never exceeds `m`, C+H never exceed `b − m`; a saturated group neither delays the other nor holds the in-flight slots against it, and the limiter grants each request at its earliest allowed instant, not later (Task 2).
2. After a `429` no request starts until `max(Retry-After, 300 s)` has passed, repeated `429`s double up to 1 h, earlier starts still count after the pause, a waiting request sends nothing, and a `418` stops the run; candle requests (a separate client) continue, also while funding raises, hangs or is paused (Tasks 1, 3).
3. No request is made without `startTime`, with `limit` other than 1000, with `start > end`, or for a symbol that is not a verified, **active** USDT-M perpetual; a refused request uses no pause check, grant, slot, limiter start or network call (Task 3).
4. A failing raw call is issued once (CCXT does not retry), a `429` on the server-time request counts as the same IP limit, and a Retry-After header is only read for an HTTP 429 (Task 3).
5. `fetch-funding-once` with untrusted time makes no request; a `200 []` answer stores nothing and is not an error; a row outside the range, a duplicate key or an error object is a parse error with nothing stored; a repeated run is idempotent; the request is never refused for `start > end` (any `--hours`, any allowed delay); the stored rows never include one with `T + delay > lower_bound` (Task 4).

**Files:**

**Interfaces:**
- `RequestClass` (domain) re-exported from the limiter module.
- `MAX_IN_FLIGHT: Final = 2`; `WINDOW_MS = LIMITER_WINDOW_MS` (305 000).
- `class FundingRateLimiter(budget_per_5min: int, clock: Clock, sleep: Sleep, *, max_in_flight: int = MAX_IN_FLIGHT)`: validates `b` (`TypeError` for a non-`int` or `bool`, `ValueError` outside 50..250, via `round_share`); `m = round_share(b)`, `other = history_catchup_share(b)`; `grant(request_class: RequestClass) -> AsyncContextManager[None]`; `starts_in_window(at_ns: int, request_class: RequestClass | None = None) -> int` (read-only; `R` counts the R group, `C` or `H` count the C+H group, `None` the total).

Semantics of `grant`: enter → hold the group's FIFO lock → loop: read the clock, drop starts that left the window (a start at `s` counts while `t − 305 s < s`, i.e. it leaves at `t = s + 305 s`), if the group has room go on, otherwise sleep until the oldest counted start of the group leaves (rounded up to a whole millisecond) and re-check → acquire an in-flight slot (still holding the group lock, so the room cannot shrink) → read the clock again, record the start with that reading → release the group lock → yield. Exit releases the slot. A cancellation anywhere before the start is recorded records nothing, holds neither lock nor slot afterwards; a cancellation after it (before or during the call) leaves the start counted (the start was granted). The cap of R is `m`, the cap of C and H together is `b − m`; because they sum to `b` the total never exceeds `b`.
