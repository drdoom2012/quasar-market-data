# FR-4 Funding Rate Task Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `quasar-collector run` collects funding rate history continuously when the configuration has an enabled `[funding_rate]` table: hourly rounds, a deterministic scheduler with the work classes S, R, C and H, bounded backward backfill, forward catch-up after an outage, restart reconcile, suspension of failing series, an hourly measurement line, and isolation from candle collection (issue #19, ADR-0004 P-9 to P-12, P-15 rows marked FR-4, P-16).

**Architecture:** Pure rules in `domain` (round schedule, suspension book, series planner and the total-order selection of ADR-0004 P-10). In `config`: the optional `[funding_rate]` table. In `collector`: a read-only series reader, small additions to the FR-3 limiter (room queries, peak), a measurement collector, and one asyncio task (`funding_rate_task.py`) with a single **dispatcher** loop that asks the pure selection for the next request whenever the limiter has room, runs each request as one page in its own worker (at most 2), applies the result (FR-2 writer with the final-transaction `merge`) and owns rounds, deadlines, suspension, logging and the hourly line. `cli.run` starts the task after the candle loop's first round and post-check, exactly as for open interest; any exception ends only that task.

**Tech Stack:** Python 3.12, asyncio, pytest, mypy strict, ruff, import-linter, `ManualTime` from `tests/collector/manual_time.py`.

**Spec:** `docs/adr/0004-funding-rate.md` (P-5, P-7, P-8, P-9, P-10, P-11, P-12, P-15 rows for FR-4, P-16), FR-1 to FR-3 (merged), issue #19. Patterns: `collector/open_interest_task.py` (start gate, `sleep_or_stop`, `_run_until`, measurement cadence, `emit`), `collector/cli.py` (`_open_interest_main`, `_open_interest_run`, `_finish_open_interest`, `CandleWriteHooks`), `config/settings.py` (`_open_interest`), `collector/open_interest_measurements.py`, `collector/open_interest_reader.py`, `tests/collector/open_interest_task_fakes.py` (`make_rig`, `track_executor`), `tests/collector/test_binance_usdm_funding_rate.py` (`FakeExchange`), `docs/superpowers/plans/2026-11-02-oi-4-open-interest-task.md`.

## Decisions this plan makes (not fixed by the ADR)

Approved by the user on 2026-11-05 (asked with the plan review): **(a)** the capacity simulations for `b = 150`, `b = 250` and the 200-round runs are not in `make check` but behind a pytest marker `simulation` and a new `make simulate`; `b = 50` stays in `make check`; **(b)** the capacity refusal applies only when `enabled = true` (key ranges are validated always); **(c)** failure policy: retry after 1 s, then 2 s, the third consecutive failure suspends the series.

- **One dispatcher, one page per request.** ADR P-10 selects "at each grant opportunity". The task keeps a dispatcher loop: when a worker slot is free and the limiter has room for the class's group, ask the pure `select_next(...)` for the next `Plan`, start a worker for that **single page**, yield once, repeat. Rounds, catch-up and history run in the same loop at the same time; a round only enables S and R. A multi-page history chunk or forward range is a sequence of single-page plans on one series, so every page is a selection opportunity (the `turn` alternation and "stays first in H until the last page" hold page by page). Earlier pages of a history chunk are written without a `merge`; the last page carries the `merge` of the whole chunk (P-7).
- **`HistoryChunk.next_start_ms` advances only when the page's `write` returned.** A failed or cancelled page repeats the same start (every row transaction but the last is known to have committed, P-7). After an unknown outcome of the final page the chunk is kept (re-merging is idempotent); a re-read that shows `from_ms != chunk.through_ms + 1` drops the chunk.
- **Selection is a pure function of explicit inputs** (`domain/funding_rate_scheduler.py`): per series a `SeriesStatus`, the flags `round_active`, `r_room`, `ch_room`, the toggle `turn`, `b_now_ms`, `recheck_ms`, `backfill_days`. It returns the next `Plan` (symbol, `kind` in S / R / C / H, `request_class`, start, end, chunk) and the new `turn`, or `None`. Same inputs, same output; every ordering ends in `symbol`. `turn` flips when a C/H plan is **selected** (the worker may then fail before its grant; documented, harmless). All time inputs of the planner and of the retry / suspension book are on the **monotonic** clock in ms; only round boundaries and `verified_at_ms` are wall-clock.
- **Class eligibility follows the ADR text** (review finding 1, no reading): `S` = no span and the round is active; `R` = a span, **not `continuing`**, round active, not yet asked in this round, range `[max(from_ms, through_ms − recheck_ms), b_now]`, first page only; `C` = `continuing_from_ms` set, range `[a', b_now]`; `H` = `history_pending` with the next chunk or the next page of the current chunk. `behind` is **informational** (the log and, in FR-5, the API); it does not move a series between classes at planning time. Only the **start-up reconcile** (P-11 step 2) sets `continuing_from_ms = through_ms + 1` for a series that is `behind` at start ("treated as continuing after a restart"). A truncated S, R or C page sets `continuing_from_ms = last`; a non-truncated one clears it. A series skipped once therefore stays an R candidate and comes first in the next round (rule 1). A series is "asked in this round" when its request succeeded or it was suspended; a failed one stays eligible after its delay. Series that are `continuing` and not asked in a round are not counted as skipped.
- **Time and `b_now`.** `L = server_lower_bound(observation, …)` is evaluated **once right after each observation**, and `b_now = forward_end_bound_ms(delay, L)` is the end bound of every forward request until the next observation (a lower bound stays a lower bound as time passes, as in OI-4). Observations: one per round at wake (class R, "index 0", counted in `N = S + 1`) and, **only when it is needed**, one at task start: when the start-up reconcile finds series with `continuing_from_ms` set (behind) **and** the next wake is more than `Wl` (305 s) away, so the extra R start cannot delay the first round's last group (review finding 4); otherwise catch-up waits for the round's observation. Untrusted time or a failed observation at wake skips the round (logged `funding-warning round-skipped`); the previous `b_now` stays valid for C; with no bound ever, C and S/R wait while H still runs (backward chunks need no clock, P-4). A round that cannot start because of a pause past its deadline is logged.
- **`verified_at_ms`** passed to a `merge` is `clock.wall_ms()` at the send for S, R and C, and the series' **current** `verified_at_ms` for H (the SQL `max` leaves it unchanged), so a history chunk never makes a series whose R was skipped look freshly verified and rule 1's order holds. The in-memory value is `max(old, passed)` (the write report carries no `verified_at_ms`).
- **Rounds** have the shape of OI: `wake(B) = B + round_offset_ms`, `deadline(B) = B + 3 600 000 − 15 000`; `next_round(now, last_boundary, offset)` returns the boundary, its wake and how many boundaries were skipped. The round's observation runs as a scoped job (the `_run_until` shape) that is cancelled at the deadline or on `stop`. At the deadline the S/R workers of the round are cancelled; unstarted series are counted `skipped` and logged, **nothing is marked failed**; C and H workers are not cancelled by a round deadline. `funding-round` is emitted when the round's S/R work is done or at the deadline, whichever comes first.
- **Liveness.** Every worker has a task-level timeout (`REQUEST_TIMEOUT_MS = 30_000`, a constant above CCXT's own 10 s): a fetch that exceeds it is a series failure; if it fires inside the write the outcome is unknown and the series is flagged `needs_reread`. Two hung C/H pages therefore cannot hold both slots beyond the timeout, and neither the round's observation nor `stop` is ever awaited inline.
- **Failures and suspension (P-10, approved above).** A failed request (source error other than pause / stop, request timeout, parse error, selection error, a write failure, `FundingSpanNotAdjacentError`, an unknown outcome) is counted per series with the retry delay 1 s, then 2 s (`RETRY_DELAYS_MS = (1_000, 2_000)`, in memory); the third consecutive failure suspends the series for 6 h, repeats for 12 h then 24 h; after expiry one probe: success clears everything, a failure suspends again with the next duration. `FundingRateRequestRefused` is such a failure and is logged `funding-error request-refused`. A non-adjacent merge is a series failure plus a re-read of the span (a planning bug or stale memory must not end the task). `429`/`418` are not series failures: `ExtensionPaused` makes the dispatcher wait until the pause ends (workers in flight finish); `ExtensionStopped` ends the task by raising; an **unusable writer** (`writer.unusable` is true, or a write error that is neither busy nor an unknown outcome and not a non-adjacent merge) ends the task (`FundingRateWriterUnusable`). `AsyncFundingRateWriter` exposes `unusable`.
- **Late events (P-8)**: a row in `inserted_keys` of a forward page with `span_before.from_ms <= funding_time_ms <= span_before.through_ms` is stored, logged `funding-warning late-event` and counted; H rows are not late. After a failed page the planned span classifies `partial.inserted_keys` the same way (FR-2 handoff).
- **Output lines** (one injected `emit(line)`; `cli` sends lines starting `funding-warning` or `funding-error` to stderr, the rest to stdout): `funding-reconcile` (per series and a total, once at start), `funding-round`, `funding-conflict` (once per newly recorded conflict), `funding-suspended` / `funding-probe`, `funding-warning`, `funding-error`, `funding-budget` (both extension budgets at start, only when funding is enabled), `funding-measurement` (hourly).
- **Hourly line** (P-9 rule 5, issue #19): `funding-measurement` with the peak funding request starts per 305 s (from the limiter), mean request time `d̄`, `off_hour_rows`, late events, skipped series, conflicts, p50 / p99 / max (nearest rank) of 100-row transactions (`funding100_*`) and of all transactions, plus the candle write p99 from the hook. Counters reset every hour of monotonic time; a last line on a clean stop if anything was collected.
- **Symbols.** The task collects the symbols of the configured venue (`venues[0].symbols`, as OI): "funding is collected for every symbol of the venue" read as the configured universe, because there is no second list (P-12). The capacity of P-10 is checked against `len(symbols)` at configuration parse time (only when enabled) and again, as a defensive check, when `run` builds the task config. `FundingRateTaskConfig` itself does **not** call `assess_capacity`, so the isolated-round simulation can build one beyond `S_sustained`.
- **Config constants** come from the funding domain modules, imported under aliases (`config/settings.py` already defines OI values with the same names): budget 50..250 and offset 60 000..600 000 from `domain/funding_rate_capacity.py`, `backfill_days` 1..3650 from `domain/funding_rate_span.py`, and the delay maximum `MAX_FUNDING_RATE_PUBLICATION_DELAY_MS = 595_000`, **moved** to `domain/funding_rate.py` (the FR-3 module `fetch_funding_rate_once.py` keeps its public name `MAX_PUBLICATION_DELAY_MS` as an alias of it).
- **Reader:** one short read-only transaction **per series** on `asyncio.to_thread` (P-11 "one bounded read per series"), wrapped in `FundingRateReadError(StorageError)`; no long-lived snapshot over all series.
- **Limiter additions (FR-3 module, read-only API):** `room(request_class, at_ns) -> bool` (the group's counted starts plus requests waiting in `grant` are below the cap), `next_room_ns(request_class, at_ns) -> int`, `peak_starts() -> int`. A `waiting` counter per group is incremented when `grant` is entered and decremented when the start is recorded or the wait is cancelled. The scheme depends on the real source reaching the group lock with no `await` before it (verified: two starts are recorded after one `sleep(0)`); **tests therefore drive the real `BinanceUsdmFundingRateSource` with a fake CCXT exchange**, never a hand-written source that awaits first. The dispatcher yields once after starting a worker.
- **Test doubles.** `FakeFundingExchange` (new name; `FakeFundingSource` already exists for FR-3) with request time on `ManualTime`, per-symbol settlement generators, failure schedules, `429`/`418`, a hang switch and a `served` log; the real writer on `tmp_path` uses `ManualTime.track_executor(writer._executor)` (the F-19 race). **Simulations** (Task 7) and the task-level starvation test use an in-memory `FundingRateSink` that applies `merge_span` and reports `span_before` / `span_after` / `inserted_keys` (E-14 modelled writes as instant); the real writer stays in the storage, crash and contention tests. The planner input is maintained incrementally in the task, not rebuilt per decision.
- **`Plan.kind`** distinguishes S from R (both class R); needed for "S before R" and for the logs.

## Review Focus

1. Determinism and total order of `select_next` against a brute-force model; `UNSEEDED` first, then `verified_at_ms`, then `symbol`; `turn` alternation; H serves a never-served series first, then smallest `last_served`; a series with a chunk in progress stays first in H (Task 2).
2. The span never covers a settlement whose row is not stored, for every page kind and every failure point, including a timeout, a cancellation at the deadline and an unknown final-transaction outcome; restart converges with no duplicate and no conflict (Tasks 5, 6).
3. History cannot starve behind catch-up and the reverse; rounds keep their planned start times with C/H saturating; no class exceeds its cap; one series never has two requests in flight; hung C/H pages cannot stall a round (Tasks 6, 7).
4. 48 consecutive rounds at `S_sustained` for `b = 50, 150, 250`: no skip, no drift, last start at least 30 s before the deadline; the isolated-round capacity is not sustainable (Task 7).
5. Isolation: a funding source that raises, hangs or answers 429 leaves candle round reports (results and `lateness_ms`) identical to the run without funding; disabled or absent config creates nothing (Task 8).
6. Config: every bad value is an error naming the key; the capacity refusal only when enabled (Task 1).
