# FR-4 Funding Rate Task Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `quasar-collector run` collects funding rate history continuously when the configuration has an enabled `[funding_rate]` table: hourly rounds, a deterministic scheduler with the work classes S, R, C and H, bounded backward backfill, forward catch-up after an outage, restart reconcile, suspension of failing series, an hourly measurement line, and isolation from candle collection (issue #19, ADR-0004 P-9 to P-12, P-15 rows marked FR-4, P-16).

**Architecture:** Pure rules in `domain` (round schedule, suspension book, series planner and the total-order selection of ADR-0004 P-10). In `config`: the optional `[funding_rate]` table with the capacity check. In `collector`: a read-only series reader, small additions to the FR-3 limiter (room queries, peak), a measurement collector, and one asyncio task (`funding_rate_task.py`) with a single **dispatcher** loop that asks the pure selection for the next request whenever the limiter has room, runs each request as one page in its own worker (at most 2), applies the result (FR-2 writer with the final-transaction `merge`) and owns rounds, deadlines, suspension, logging and the hourly line. `cli.run` starts the task after the candle loop's first round and post-check, exactly as for open interest; any exception ends only that task.

**Tech Stack:** Python 3.12, asyncio, pytest, mypy strict, ruff, import-linter, `ManualTime` from `tests/collector/manual_time.py`.

**Spec:** `docs/adr/0004-funding-rate.md` (P-5, P-7, P-8, P-9, P-10, P-11, P-12, P-15 rows for FR-4, P-16), FR-1 to FR-3 (merged), issue #19. Patterns: `collector/open_interest_task.py` (start gate, `sleep_or_stop`, `_run_until`, measurement cadence, `emit`), `collector/cli.py` (`_open_interest_main`, `_open_interest_run`, `_finish_open_interest`, `CandleWriteHooks`), `config/settings.py` (`_open_interest`), `collector/open_interest_measurements.py`, `collector/hole_reader.py`, `tests/collector/open_interest_task_fakes.py`, `docs/superpowers/plans/2026-11-02-oi-4-open-interest-task.md`.

## Decisions this plan makes (not fixed by the ADR)

- **One dispatcher, one page per request.** ADR P-10 selects "at each grant opportunity". The task keeps a dispatcher loop: build the `SeriesStatus` list, ask the pure `select_next(...)` for the next `Plan` when a worker slot is free and the limiter has room for the class's group, start a worker for that **single page**, repeat. Rounds, catch-up and history run in the same loop at the same time; the round only enables classes S and R. A multi-page history chunk or forward range is a sequence of single-page plans on one series, so every page is a selection opportunity (the "turn" alternation and "stays first in H until the last page" of the ADR hold page by page). Earlier pages of a history chunk are written without a `merge`; the last page carries the `merge` of the whole chunk (P-7).
- **Selection is a pure function of explicit inputs** (`domain/funding_rate_scheduler.py`): per series a `SeriesStatus` (span, `verified_at_ms`, `busy`, `unavailable_until_ms`, `continuing_from_ms`, `history_chunk`, `never_served`, `last_served`, `asked_in_round`), the flags `round_active`, `r_room`, `ch_room`, the toggle `turn`, `b_now_ms`, `recheck_ms`, `backfill_days`. It returns the next `Plan` (symbol, class, start, end, final-page information) and the new `turn`, or `None`. Same inputs, same output; every ordering ends in `symbol`.
- **Class eligibility (P-10, with the readings below):** `S` = no span and the round is active; `R` = a span, not `continuing`, not `behind`, round active, not yet asked in this round, request range `[max(from_ms, through_ms − recheck_ms), b_now]` first page; `C` = `continuing_from_ms` set, or `behind` after a restart (treated as `continuing` from `through_ms + 1`), range `[a', b_now]`; `H` = `history_pending` with the next chunk or the next page of the current chunk. A series is not eligible for any class while `busy`, suspended, or inside the retry delay after a failure. **Reading:** a `continuing` or `behind` series is served by class C and is not an R candidate until it has caught up (otherwise R would repeat the first page that C is about to continue). A series is marked "asked in this round" when its request succeeded or when it was suspended; a failed one stays eligible after its delay (the retry is another selection inside the same class share).
- **Time and `b_now`.** `L` = `server_lower_bound(observation, …)` is evaluated **once right after each observation** and `b_now = L − publication_delay_ms` (FR-1 `forward_end_bound_ms`) is the end bound of every forward request until the next observation; a lower bound stays a lower bound as time passes (as in OI-4). Observations: one at task start (class R, so catch-up can begin before the first round) and one per round at wake (class R, "index 0"). Untrusted time at wake skips the round (logged); with no trusted bound class C and S/R wait and H still runs (backward chunks need no clock, P-4).
- **Rounds** reuse the shape of OI: `wake(B) = B + round_offset_ms`, `deadline(B) = B + 3 600 000 − 15 000`; `next_round(now, last_boundary, offset)` returns the boundary to run, its wake and how many boundaries were skipped. At the deadline the S/R workers of the round are cancelled; series not started are counted as `skipped` and logged; **nothing is marked failed**; C and H workers are not cancelled by a round deadline. After a cancellation inside the writer the outcome of that page is unknown: the series is flagged `needs_reread` and its span is re-read from the database before it is planned again (P-7 crash table).
- **Failures and suspension (P-10).** A failed request (source error other than pause/stop, parse error, selection error, write failure, unknown outcome) is counted per series with a retry delay of 1, 2, 4 s (constants, in memory) and counts toward suspension: the third consecutive failure suspends the series for 6 h, repeats for 12 h then 24 h; after expiry one probe: success clears everything, a failure suspends again with the next duration. A `429`/`418` is not a series failure. `ExtensionPaused` makes the dispatcher wait until the pause ends (workers in flight finish); `ExtensionStopped` and an unusable writer (a write error that is neither busy nor an unknown outcome) end the task by raising, like OI.
- **Late events (P-8)** are detected from the write report: a row in `inserted_keys` of a forward page with `span_before.from_ms <= funding_time_ms <= span_before.through_ms` is stored, logged at warning level (`funding-warning late-event`, symbol and time) and counted. After a failed page the caller classifies `partial.inserted_keys` against the span it planned with (FR-2 handoff), so the same rule is applied with the planned span.
- **Output lines** (one injected `emit(line)`; `cli` sends lines starting `funding-warning` or `funding-error` to stderr, the rest to stdout): `funding-reconcile` (per series and a total, once at start), `funding-round` (per round), `funding-conflict` (once per newly recorded conflict), `funding-suspended` / `funding-probe`, `funding-warning`, `funding-error`, `funding-measurement` (hourly).
- **Hourly line** (P-9 rule 5, issue #19): `funding-measurement` with the peak funding request starts per 305 s (from the limiter), mean request time `d̄`, `off_hour_rows`, late events, skipped series, conflicts, and the p50/p99/max of 100-row transactions and of all transactions (nearest rank), plus the candle write p99 reported by the hook. Counters reset every hour of monotonic time; a last line on a clean stop if anything was collected.
- **Symbols.** The task collects the symbols of the configured venue (`venues[0].symbols`, as OI): "funding is collected for every symbol of the venue" read as the configured universe, because there is no second list (P-12). The capacity of P-10 is checked against `len(symbols)` at configuration parse time.
- **Limiter additions (FR-3 module, read-only API):** `room(request_class, at_ns) -> bool` (the group's counted starts plus requests waiting in `grant` are below the cap), `next_room_ns(request_class, at_ns) -> int`, `peak_starts() -> int` (the largest total of counted starts seen at a grant since the last call, then reset). A `waiting` counter per group is incremented when `grant` is entered and decremented when the start is recorded or the wait is cancelled, so the dispatcher never over-reserves a group. The worker's first await is the fetch, and the dispatcher yields once after starting a worker so the reservation exists before the next decision.
- **Simulation tests (P-15 Capacity rows).** A harness drives the real task with `ManualTime`, the real limiter and a fake source with a configurable request time and failure rate. If the 48-round runs for `b = 150` and `250` make the default suite slower than about a minute, they move behind a pytest marker `simulation`, deselected in `make check` and run by `make simulate`; `b = 50` stays in the default suite. This is reported in the PR.

## Review Focus

1. Determinism and total order of `select_next` against a brute-force model; `UNSEEDED` first, then `verified_at_ms`, then `symbol`; `turn` alternation; H serves a never-served series first, then smallest `last_served`; a series with a chunk in progress stays first in H (Task 2).
2. The span never covers a settlement whose row is not stored, for every page class and every failure point, including a cancellation at the deadline and an unknown final-transaction outcome; restart converges (Tasks 5, 6).
3. History cannot starve behind catch-up and the reverse; rounds keep their planned start times with C/H saturating; no class exceeds its cap; one series never has two requests in flight (Tasks 6, 9).
4. 48 consecutive rounds at `S_sustained` for `b = 50, 150, 250`: no skip, no drift, last start at least 30 s before the deadline; the isolated-round capacity is not sustainable (Task 9).
5. Isolation: a funding source that raises, hangs or answers 429 leaves candle round reports (results and `lateness_ms`) identical to the run without funding; disabled or absent config creates nothing (Task 8).
6. Config: every bad value is an error naming the key (Task 1).
