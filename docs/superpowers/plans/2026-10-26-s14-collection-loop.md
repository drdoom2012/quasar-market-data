# S14 Collection Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `quasar-collector run` collects the newest closed candles of a configured list of symbols on every UTC boundary plus publication delay, with bounded concurrency, a spacing limit on adapter calls, a bounded retry for candles that are not yet confirmable, and a shutdown that never cancels a running attempt before its grace and reports honestly what it could not settle.

**Architecture:** The loop is a new collector module that calls the existing `fetch_once` once per symbol and attempt, so INV-007 holds by construction: the closed-candle selection stays the single gate and no second ingestion path appears. S13's `next_wake_ms` and `newest_expected_open_ms` decide when to look and which slot a round must obtain; `clock.wall_ms()` is passed in. A decorator over `KlineSource` spaces the adapter calls, so the source and `fetch_once` logic stay unchanged. The one change to `fetch_once.py` besides the `Clock` move is a type-only `CandleSink` protocol for its `writer` parameter, so the loop can track writes and tests can drive them. No schema, contract, ADR or domain change.

**Tech Stack:** Python 3.12 stdlib (`asyncio`, `signal`, `threading` in one test), existing `fetch_once`, `AsyncCandleWriter`, `BinanceUsdmSource`; pytest, mypy strict, ruff, import-linter. No new dependency.

**Spec:** `docs/superpowers/specs/2026-10-20-market-data-v1-design.md` (§8 S14, D5, §11.2 and §11.9), `docs/architecture.md` (Scheduler, Ingestion, §6 and §9 safe shutdown), `docs/adr/0001-binance-ingestion-fidelity-and-closed-candles.md` (P-3, P-4, P-5, P-6, D-E). Earlier plans: `2026-10-22-s9-fetch-once-cli.md`, `2026-10-26-s13-scheduler-planner.md`.

## Facts checked in the repository (2026-10-26)

Verified by reading the code, or by a command where stated:

- `fetch_once(source, writer, config, clock) -> FetchOnceReport` (`collector/fetch_once.py`) observes server time, fetches klines, parses, selects and calls `writer.write(selection.eligible, ingested_at_ms=...)` only when `selection.eligible` is non-empty. It raises `SourceError`, `KlineParseError` and writer errors unchanged. `FetchOnceReport` has `fetched`, `selection` (`eligible: tuple[ValidatedCandle, ...]`, `pending`, `invalid`, `untrusted_reason`) and `write: WriteReport | None`. `ValidatedCandle` is a `NewType` of `Candle`, so `.open_time_ms` exists.
- `WriteReport` (`candle_writer.py`) is `inserted: int`, `duplicates: int`, `conflicts: tuple[CandleConflict, ...]`; `CandleConflict` has `incoming: Candle` and `stored: Candle`. **The conflicting slot is therefore known** (`conflict.incoming.key.open_time_ms`), but insert versus duplicate is only a count, not per candle. A batch is one transaction: a returned `WriteReport` means the whole batch was committed (inserts and recorded conflicts) and nothing in it is in doubt.
- `CandleWriter.write` raises `CandleWriteOutcomeUnknown` only when `COMMIT` failed with the outcome unknown; the batch is atomic and re-sending is safe. Other `CandleWriteError` subclasses of `StorageError` mean "nothing was written" or "writer unusable".
- `AsyncCandleWriter.write` runs the job on one FIFO worker thread via `run_in_executor`. Cancelling the awaiting task does not stop a running job: the job completes (commit or rollback) on the thread, the caller never learns the result (module docstring, INV-033).
- **`AsyncCandleWriter.close()` has no time bound.** It queues `CandleWriter.close` behind every accepted write on the same FIFO thread, then `executor.shutdown()` (waits for the thread) in the default executor, all shielded. A write blocked on a SQLite lock is bounded per lock wait by `busy_timeout` (`DEFAULT_BUSY_TIMEOUT_MS = 5000`), not by one total deadline. So the time `close()` takes is not bounded by anything in this slice, and a grace timeout on the fetch tasks does not bound the process exit.
- `cli._close_quietly` turns any `Exception` from a close into a stderr warning. That is the `fetch-once` behaviour; `run` needs a stricter one for the writer (Decision 9).
- **Source timeouts (checked by running `ccxt.async_support.binanceusdm()` in this environment):** `exchange.timeout == 10000` (ms), `enableRateLimit is True`, `rateLimit == 50` (ms). `BinanceUsdmSource` sets none of them. Not verified: whether the 10 s is enforced as a total per request and whether CCXT retries internally; this plan does not depend on either.
- `Clock` and `SystemClock` live in `fetch_once.py`; `cli.py` imports them from there. `tests/collector/fetch_fakes.py` has `FakeClock` (`advance(ms)`) and `FakeSource` (each fetch call advances the clock by `rtt_ms`). `tests/collector/faulty_connection.py` exists for write-failure tests.
- `fetch_once` calls `server_lower_bound(..., None, ...)`, so each call starts with no previous observation; W-6 (server time never regresses, ADR-0001 P-4) is not checked across calls today.
- Not verified: nothing in this plan has been run. Binance's request-weight limits were not read; the default request spacing below is a placeholder to confirm before a live run with many symbols.

## Global Constraints

- Collector and API stay independent; domain imports nothing from `collector`, `api`, `storage`, ccxt, fastapi, talib or `sqlite3`, and is not touched. The loop lives in `collector`.
- Every candle reaches the writer only through `fetch_once` (INV-007). The loop never fetches rows itself and never calls `write` outside `fetch_once`.
- Persist only confirmed closed candles; a pending or forming candle is never stored and never replaced by a guess (ADR-0001 D-E, P-5). Running out of retries is reported, not hidden.
- Fail closed: untrusted server time confirms nothing; a failing symbol does not stop the others; a storage failure that is not an unknown outcome stops the whole process with a non-zero exit.
- Restart-safe and idempotent: a restart re-collects the newest rows and the writer treats duplicates as no-ops. Gap recovery beyond `limit` rows is S15/S16, not this slice.
- A conflict is never overwritten and never retried into a different result (ADR-0001 P-6, S8).
- No schema, public-contract or ADR change. No new dependency, no live-exchange test in the default suite, tests never touch production storage.
- Verification: `make check` before **every** commit; during a task `uv run pytest <path>`. No other commands are invented.

## Decisions made in this plan (open to review)

1. **Reuse `fetch_once` per symbol and attempt.** It is the tested gate. Cost: two requests per symbol per attempt (server time, klines). A shared per-round server-time observation would halve that but changes `fetch_once`; not done now, measure in S23 first.
2. **A round targets one slot; `COLLECTED` means that slot is confirmed stored and equal to the exchange data.** A round starting at wall time `t` has `target = newest_expected_open_ms(t, ...)`. After an attempt's `fetch_once` returns, the symbol is classified:
   - `target` is in `report.selection.eligible` **and** `report.write` is not `None` (it must be, `eligible` is non-empty) **and** no `conflict.incoming.key.open_time_ms` in `report.write.conflicts` equals `target` → `COLLECTED`. The batch is committed atomically, so the target is either newly inserted or already stored with identical values (the report does not say which, and the plan does not need it). An eligible target alone is not enough; the returned write report is.
   - `target` is among the conflicts → `CONFLICTED`. The writer kept the stored candle and recorded the differing one (INV-034). **Not retried:** a retry would see the same conflict. The slot is reported; coverage shows it conflicted. This is the target slot's conflict.
   - Conflicts at other open times are not about the target: they are listed in `SymbolResult.conflict_open_times` (known from the report, slot by slot) and do not change the target's outcome.
   - Otherwise the target is pending, invalid or time is untrusted → retry. `last_problem` says `time untrusted: <reason>` when `selection.untrusted_reason` is set, else `target not confirmed (pending=<n>, invalid=<n>)`. The plan does not read the invalid candles' slots (their structure was not checked here).
   - `CandleWriteOutcomeUnknown` from the attempt is retried: the next attempt re-sends the newest rows, which may be a **different batch**. `COLLECTED` requires the returned write report of the attempt that classifies the target; it says nothing about the earlier unknown write. That uncertainty is tracked separately and persists (Decision 9).
   - `target_open_ms is None` (nothing is expected yet): one attempt, outcome `NOTHING_EXPECTED`.
3. **Bounded retry, no claim about round length.** `RetryPolicy`: `max_attempts`, `initial_delay_ms`, `max_delay_ms`; defaults 6, 1 000, 8 000 (waits 1, 2, 4, 8, 8 s). The earlier check "total backoff wait < timeframe" is **removed**: it guaranteed nothing, because attempts, adapter calls, limiter waits and writes also take time. What actually keeps order is Decision 4. The only bounds the loop relies on: the attempt count, the per-request timeout of the source (CCXT 10 s default, see Facts, unchanged and not re-enforced here), the limiter queue (at most `max_concurrency` waiters, each waits for at most `min_interval_ms` per place in the queue), and SQLite's `busy_timeout` per lock wait. **No new deadline is introduced**; the worst-case round duration is therefore not bounded by a stated number in this slice, and the plan does not promise one.
4. **Rounds never overlap and never burst.** The next wake is computed from `clock.wall_ms()` after the round ends, so a slow round skips boundaries instead of queueing them. Skipped slots are picked up only because each fetch asks for the newest `limit` rows (incidental, not a guarantee); recovery is S16.
5. **First round at start**, unless stop was requested before it. Then boundary-driven.
6. **Bounded concurrency** = `asyncio.Semaphore(max_concurrency)` over symbols (default 4). A task that has acquired the semaphore re-checks `stop` before its first attempt, so a stop or fatal error leaves the tasks that were still queued unstarted (`STOPPED`, `attempts == 0`).
7. **Rate limiter spaces the real adapter calls; it does not reserve future times.** `RateLimiter(min_interval_ms, clock, sleep)`; `acquire()` holds an `asyncio.Lock` (FIFO), then loops: read `now = clock.monotonic_ns()`; `remaining_ns = last_start_ns + interval_ns - now`; if `remaining_ns <= 0` set `last_start_ns = now` and return; else `await sleep(ceil(remaining_ns / 1_000_000))` and **loop again** (re-read monotonic time after every wake, so an early or late wake is corrected). Properties:
   - **Where the start is measured:** `last_start_ns` is set at the grant, which is immediately before `RateLimitedSource` calls the inner adapter method (no `await` in between). The guarantee is: consecutive inner-source calls, all symbols together, begin at least `min_interval_ms` apart on the monotonic clock.
   - **Rounding:** waits are rounded **up** to whole milliseconds, so a fraction of a millisecond never lets a call start early.
   - **Delayed wake of several waiters does not burst:** only the lock holder waits; the next waiter acquires the lock only after the holder was granted and `last_start_ns` moved, and then waits a full interval itself.
   - **Cancellation:** a cancelled waiter, whether queued on the lock or sleeping, consumes nothing (no reservation exists); the lock is released and the next waiter measures from the last real start.
   - **Not guaranteed:** wire-level spacing. CCXT has its own throttle (`enableRateLimit True`, `rateLimit 50`, Facts) that may delay a call after our grant. That can only add delay in front of the network, but this plan does not claim a spacing of network requests, nor compliance with Binance's weight limits.
8. **Failure classes.** `SourceError`, `KlineParseError`, `CandleWriteOutcomeUnknown`: per-symbol, retried. `CandleWriteError` (not unknown), `StorageError`, `sqlite3.Error` and every other `Exception`: **fatal** (an unclassified error is never swallowed). `CancelledError`/`KeyboardInterrupt` are not failures and propagate.
9. **Stop, fatal error, grace and exit codes.**
   - `stop: asyncio.Event` is set by SIGINT/SIGTERM (CLI) or by the loop itself on a fatal error (documented: the loop sets `stop`). Once set, no new attempt starts, no retry wait is begun, no round starts, and tasks queued on the semaphore never start. Attempts already running are not cancelled before the grace ends.
   - **Grace** (`shutdown_grace_ms`, default 10 000) applies only to the **running attempts** (source calls and their writes). It is measured by the injected `sleep`, so tests drive it. **One timer per shutdown:** the grace starts when the loop first *observes* `stop` (whether or not any task raised), is created exactly once, and is never restarted or extended by a later event (a second fatal error, a repeated signal). The stop-wait task has served its purpose once it completed: from then on **only unfinished symbol tasks and the grace timer are waited on** (finished symbol tasks also leave the wait set as they complete), so an already completed task never makes the wait return at once. When the grace ends first, the remaining symbol tasks are cancelled, **awaited**, and only then judged (next bullet). The stop-wait task and the timer task are cancelled and awaited on every path.
   - **Results of tasks cancelled at grace expiry.** A task that finished normally keeps its real `SymbolResult`. For each task the coordinator itself cancelled because the grace expired, the coordinator builds a replacement `SymbolResult(symbol, outcome=STOPPED, attempts=None, inserted=None, last_write=None, conflict_open_times=None, last_problem="shutdown grace expired")`. `None` means *unknown*: the cancelled task's progress (attempts made, rows inserted, the last report) is lost with it, and the coordinator does not guess, in particular it does not report `0`. These fields exist as real values only on results the symbol task itself returned. The replacement never touches `uncertain_symbols`: that comes only from the process-lifetime `_WriteWatch` flags, which a cancelled write has already set itself (a fetch-only cancellation sets nothing). `task.result()` is never called on a cancelled task; the decision is made from `task.cancelled()` after the await, and the `CancelledError` of a task the coordinator cancelled is consumed by `gather(..., return_exceptions=True)` and never replaces the `LoopExit` or `FatalLoopError`. Cancellation of `run_collection_loop` itself is a different case: it is not consumed, the coordinator cancels and awaits its children in `finally` and the `CancelledError` propagates.
   - **Fatal errors are caught inside the symbol task.** The task wrapper (`async with semaphore:` then re-check `stop`, then `collect_symbol`) catches `Exception` raised by `collect_symbol` (by construction only fatal classes reach it, Decision 8), records the first one in a shared list, calls `stop.set()` **before the semaphore is released**, and returns a `FATAL` result instead of raising. The next task that acquires the semaphore therefore always sees `stop` and never calls the source. `CancelledError` is a `BaseException`, is not caught and propagates; per-symbol retryable errors never reach the wrapper and never set `stop`. Later fatal errors in the same shutdown do not replace the first and do not change the grace.
   - **Write uncertainty is sticky and per symbol.** The loop creates one `_WriteWatch` per symbol for the **whole process run** and hands it to `fetch_once` as the sink. The watch sets `uncertain = True` when its `write` raises `CandleWriteOutcomeUnknown` **or** is interrupted by `CancelledError` (a queued or running write whose caller was cancelled cannot know its result, `AsyncCandleWriter` docstring). **Nothing ever clears the flag during the run:** not a later `SourceError`, an attempt without a write, `STOPPED`, a successful write, a new round or a `COLLECTED` target. Reason: a later `fetch_once` may return a different batch, and the success of that batch does not prove what happened to the earlier one; proving it would need the identity of the batch and a way to read it back, which is the reconciliation of S15/S16 and not part of S14. The cost is deliberate: after one unknown outcome the process ends with exit 4, even if all later rounds were clean. A fresh process starts without the flag; the operator learns from exit 4 and the log line that a restart (idempotent re-fetch of the newest rows) is the recovery, not proof. A cancelled attempt that never reached `write` leaves the flag untouched: nothing of it was written, with certainty.
   - **Target outcome and write uncertainty are two separate facts.** `SymbolResult.outcome` describes only the round's target slot (`COLLECTED`, `CONFLICTED`, `GAVE_UP`, ...). Uncertainty is reported by the loop as `uncertain_symbols` (names of symbols whose flag is set), in `RoundReport`, `LoopExit` and `FatalLoopError`.
   - **Result type.** `run_collection_loop` returns `LoopExit(uncertain_symbols: tuple[str, ...])` after a requested stop, and raises `FatalLoopError(uncertain_symbols: tuple[str, ...])` (message with the original error, `__cause__` set) after a fatal error. A round that ended in a fatal error is not passed to `on_round`.
   - **Mapping, and priority:** `LoopExit` with no uncertain symbol → **0**; `LoopExit` with uncertain symbols → **4**; `FatalLoopError` without uncertain symbols → **1**; `FatalLoopError` with uncertain symbols → **4** (an unknown write outcome outranks a fatal error because it is the fact the operator must act on; the message names both). Usage errors → **2**; a database directory that does not exist, a migration failure or a failure to open the source or writer happens before any loop work → **1**. `GAVE_UP` and `CONFLICTED` results do not change the exit code (they are logged per round).
   - **Closing resources.** The exit code is computed *before* resources close and a close problem can only worsen it: the exchange client's close failure stays a warning (it has no bearing on persistence); a failing **writer close** is printed as an error and turns an otherwise `0` exit into `1`; it never lowers `1` or `4`. `writer.close()` is awaited without a deadline (Facts: it has none): the process may outlive the grace while a blocked write settles, and the plan says so in the README; it does not promise a bounded shutdown.
   - **Task hygiene.** Every task the loop creates (symbol tasks, the stop-wait task, the grace timer, the interruptible-sleep helper's tasks) is awaited or cancelled-and-awaited on every path, including cancellation of the loop itself. A test asserts no task started by the loop remains after return or raise.
10. **`Clock` moves to `collector/clock.py`** (S13 decision 1) together with `Sleep = Callable[[int], Awaitable[None]]` (milliseconds) and `system_sleep`. `fetch_once.py` gets a type-only `CandleSink` protocol (`async def write(self, candles: Sequence[ValidatedCandle], *, ingested_at_ms: int) -> WriteReport`) as the type of its `writer` parameter; `AsyncCandleWriter` satisfies it unchanged.
11. **CLI.** `quasar-collector run --db PATH --symbol S [--symbol S ...] [--limit 100] [--publication-delay-ms 15000] [--max-concurrency 4] [--min-request-interval-ms 100]`. The universe file is S20.
12. **Out of scope, recorded as limits:** server-time regression across observations, a long cool-off after Binance 418/429, health and readiness (S17), checkpoints (S15), backfill (S16), per-symbol fairness beyond FIFO, metrics, any hard deadline on a round.

## Test time and concurrency (applies to Tasks 1 to 4)

- **`tests/collector/manual_time.py` (new): `ManualTime`.** One object is both a `Clock` and the `Sleep`. `sleep(ms)` registers a waiter (a future with `deadline_ns = now + ms * 1e6`) and awaits it; **nothing advances by itself**. API: `async advance(ms)` moves `monotonic_ns` and `wall_ms` forward to each due deadline in order, resolves the due waiters and yields to the event loop until no task is ready (`await asyncio.sleep(0)` in a bounded loop, failing the test after 1 000 yields); `async until_waiting(n)` yields until `n` waiters are registered (failing after the same bound); `waiting` (the sorted deadlines); a cancelled waiter is removed. `advance` can also be told to move by a non-multiple of a wake (a late wake): all waiters whose deadline passed wake at the same instant, which is how delayed wake-ups are created on purpose.
- **`advancing_sleep(clock: FakeClock) -> Sleep` in `fetch_fakes.py`** is only for tests with at most one waiter at a time (for example the CLI tests with `--max-concurrency 1` and one symbol); it **raises** if a second sleep starts while one is in progress, so it can never silently serialise a concurrency test.
- **Scheduling tests use asyncio-only fakes** (`FakeSource`, a `ControlledSink` whose `write` signals `write_started` and awaits `release`, both `asyncio.Event`s). They use no worker thread and no real waiting.
- **Writer-thread tests are separate** (`tests/collector/test_collection_writer_integration.py`): real `AsyncCandleWriter`, real SQLite, one test with a `threading.Event` barrier. The only real-time wait there is a 5 s safety timeout on `threading.Event.wait` that fails the test; no sleep covers a race.
- Helper `assert_no_leftover_tasks()` (in `manual_time.py`) compares `asyncio.all_tasks()` with the set before the call.

## Review Focus

Each line has its test in the named task.

1. Delayed wake of many limiter waiters (clock jumps past several deadlines at once) does not produce a burst: starts stay at least one interval apart; a sub-millisecond remainder waits a whole millisecond; cancellation while queued or sleeping consumes nothing (Task 1).
2. A target that stays pending or untrusted is retried exactly `max_attempts` times with the exact waits and never stored; an unknown write outcome retried to a returned write report is `COLLECTED`; a target conflict is `CONFLICTED` and not retried; an older-slot conflict is listed and leaves the target's outcome alone (Task 2).
3. Write uncertainty never disappears: an unknown write outcome followed by a `SourceError`, by a successful write of a *different* batch, by a clean next round, or by a stop still gives `uncertain_symbols` and exit 4; a later `COLLECTED` target does not clear it (Tasks 2 and 3).
4. Stop and fatal error: stop without any exception starts exactly one grace timer that nothing restarts or extends; queued semaphore waiters never call the source after a fatal error (even with `max_concurrency=1`); running attempts finish inside the grace; an accepted unfinished write that is cancelled at expiry stays flagged while a cancelled fetch does not (both become `STOPPED` with unknown, not zero, counts); after stop the loop blocks on real events instead of re-waiting on completed tasks; stop plus fatal error in one shutdown keeps priority 4; no helper task is left (Task 3).
5. A round that takes longer than one timeframe is followed by one round at the next future boundary, never a burst, never two overlapping rounds (Task 3).
