# FR-2 Funding Rate Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Schema version 3 with the funding rate tables, and a funding rate writer that is idempotent, records conflicts, writes the verified span only through the single adjacency-checked `merge` inside the final transaction of a page, runs on its own connection and thread, writes at most 100 rows per transaction and yields to candle writes (issue #17).

**Architecture:** One additive migration `003_funding_rate.sql` exactly as ADR-0004 P-6. A synchronous `FundingRateWriter` (one transaction of ≤ 100 rows, optionally carrying the span `merge`, per call), mirroring `OpenInterestWriter` without touching it. An asyncio front `AsyncFundingRateWriter` on its **own** single-thread executor and its **own** writer connection (`busy_timeout` 1 000 ms) that splits a page into ≤ 100-row transactions, attaches the `merge` to the **last** transaction of the page, and before each `BEGIN` waits while the existing `CandleWriteActivity` reports a candle write in flight (ADR-0004 P-7, P-8, P-9). Nothing calls the funding writer yet: the adapter is FR-3, the task and the activity entry points that call it are FR-4.

**Tech Stack:** Python 3.12, stdlib `sqlite3`, asyncio, pytest, mypy strict, ruff, import-linter.

**Spec:** `docs/adr/0004-funding-rate.md` (P-6, P-7, P-8, P-9, P-14, P-15 rows marked FR-2, P-16). Related: `docs/adr/0003-open-interest.md` (P-6, P-9), `docs/adr/0002-sqlite-schema-v1.md`, FR-1 (`domain/funding_rate.py`, `domain/funding_rate_span.py`). Patterns to mirror: `collector/open_interest_writer.py`, `collector/async_open_interest_writer.py`, `collector/candle_write_activity.py`, `tests/collector/faulty_connection.py`, `tests/storage/test_schema_v2_open_interest.py`, `tests/collector/test_open_interest_writer.py`, `tests/collector/test_async_open_interest_writer.py`, `tests/collector/test_open_interest_candle_contention.py`. ## Decisions this plan makes (not fixed by the ADR)

- **The funding writer copies, not shares, the open interest writer's machinery** (third copy of the connection check, `_failure` / `_roll_back` and the async lifecycle). The ADR leaves sharing to the plan ("Whether the code is shared with open interest or written beside it is a plan-level decision"); copying keeps `candle_writer.py` and the OI writers untouched, as in OI-2. Each docstring names its original so they change together. `WriterState` and `CandleWriteActivity` are reused (public).
- **The span `merge` is a parameter of the last transaction, not a separate call.** `FundingRateWriter.write_transaction(rows, *, ingested_at_ms, merge: SpanMerge | None = None)`; `SpanMerge(venue: str, symbol: str, interval: Interval, verified_at_ms: int)`. With a `merge`, `rows` may be empty (the page had no rows: the transaction holds only the `merge`, P-7 "Unit and success"). Without a `merge` and without rows nothing is executed. `AsyncFundingRateWriter.write(rows, *, ingested_at_ms, merge=None)` splits `rows` into ≤ 100-row chunks and attaches `merge` to the last chunk (or makes a merge-only transaction for an empty page). A backward chunk of several pages (P-7) is stored by earlier `write(rows)` calls without a `merge` and claimed by the last page's call with the union.
- **`merge` is the two statements of P-7 plus the check.** `INSERT … ON CONFLICT (venue, symbol) DO NOTHING`, then the guarded `UPDATE`, then `SELECT from_ms, through_ms`. The span must contain `[a, e]`; otherwise `ROLLBACK` of the whole transaction (the last chunk's rows too: "nothing of the final chunk is kept") and `FundingSpanNotAdjacentError(FundingRateWriteError)`. The Python function `merge_span` (FR-1) is the specification; a property test checks that SQL and `merge_span` agree.
- **The verified span is written by exactly one function.** A source-scan test asserts that `INSERT INTO funding_rate_verified` and `UPDATE funding_rate_verified` appear in one module of `src/` only, with the one function name. A span written by hand through SQL is accepted by the schema when it only grows (negative control test), which is why the register names the single writer for adjacency (ADR P-6).
- **Errors carry what FR-4 needs:** `FundingRatePageError` has `.cause`, `.committed_transactions` (confirmed commits only; an outcome-unknown transaction is not counted), `.partial` (report of the committed ones). Busy is `FundingRateWriteBusy`, outcome unknown `FundingRateWriteOutcomeUnknown`, as in OI-2. A page whose final transaction ends in `FundingSpanNotAdjacentError` has `.cause` of that type and the final chunk's rows are not stored.
- **Conflicts report whether they are new** (`newly_recorded`), for P-8's "one log line per newly recorded conflict". `FundingRateConflict(incoming, stored, newly_recorded)`.
- **Durations:** `lock_wait_ns` and `duration_ns` reported separately as in OI-2; they feed the hourly line of FR-4 and the soak (#22).
- **The 100-row measurement on the target disk is not a deliverable of FR-2.** Issue #17 lists it, but ADR-0003 amendment A-1 (approved by the user on 2026-11-02) moved the same criterion for open interest to the soak, read from the hourly measurement line, and issue #22 already lists "100-row funding transaction time on the target disk: p99 ≤ 50 ms from the hourly measurement line". FR-2 reports the durations the line needs. ****Approved by the user on 2026-11-04** (it follows the OI precedent; no benchmark tool is added).
- **`<signed-decimal-shape>`** for a column `c`: `typeof(c) = 'text' AND c <> '-0' AND <decimal-shape of body>` where `body` is `CASE WHEN substr(c, 1, 1) = '-' THEN substr(c, 2) ELSE c END`, so a leading `-` is the only sign, `-0` and bare `-` (empty body) are refused, `+1`, `--1`, `1.50`, `00.1` and any non-text are refused. A test compares the SQL check with `canonical_decimal` (FR-1's rate path) on a generated corpus so the two cannot drift.
- **Float guard is not in the schema (deviation from the wording of the P-15 Storage row and of the #17 checkbox, to approve before Task 1).** A STRICT TEXT column turns a bound REAL or INTEGER into text before the `CHECK` runs, so the schema cannot refuse "a float" (verified: bound `0.0001` is stored as `'0.0001'`; only `1e20` becomes `'1.0e+20'` and is refused). The repo already documents this for v1 and v2 (`test_bound_float_is_coerced_not_rejected`, `test_bound_number_is_coerced_not_rejected`, INV-074). The float guard lives in the domain object (`canonical_decimal` raises `TypeError`) and in the writer's `type(row) is FundingRate` check; the schema test becomes a coercion control, as in v2. **Approved by the user on 2026-11-04.**
- **"Span written by hand detected" means:** the schema accepts a non-adjacent hand-written growth (negative control), and a source scan proves that the only code that writes the span is the one `merge` function. Nothing detects a hand-written span in an existing database; INV-107 says so. **Reading approved by the user on 2026-11-04.**
- **Range of a page's rows against its `merge` is not checked by the writer.** A full page (`n = limit`) covers `[a, last − 1]` while its final chunk holds the row(s) at `last` (P-5), so the rows legitimately lie one millisecond above the claimed interval. Only the series is checked.
- **The reports carry what FR-4 needs for P-8 late events:** `inserted_keys` (the keys newly inserted by the transaction) and `span_before` (the span as it was inside the transaction before the `merge`), so FR-4 can log a late event without a second read. A late event is a new row of a **round (recheck) page** with `span_before.from_ms ≤ funding_time_ms ≤ span_before.through_ms`; a row below `from_ms` of a history chunk is not late. Only the transaction that carries the merge knows the span, so after a failed page FR-4 classifies `partial.inserted_keys` against the span it planned with (code review finding 3). Logging itself is FR-4; "one log line per newly recorded conflict" is served by `newly_recorded`.
- **The `api-v1.md` parenthetical is its own commit**, so the user can drop it.
- **Registers and docs:** invariant rows from INV-102. `README.md` "Schema upgrade" paragraph becomes "versions 2 and 3": the release that ships open interest and funding migrates 1→3 in one start (open interest is released only together with funding, so no production database has been at version 2). `docs/contracts/api-v1.md` §6.2.2 keeps its placeholder wording `<schema version of this build>`; only its parenthetical "(2 since OI-2, ADR-0003 P-6)" is brought up to date ("3 since FR-2, ADR-0004 P-6"). **Note-only edit to a contract file, to confirm in the PR.**

## Review Focus

1. A page of 250 rows (chunks 100, 100, 50) that fails in each chunk, inside the `merge`, before and after `COMMIT`: the span never covers a settlement whose row is missing, a reader never sees a span without its rows, and a restart converges to the clean-run state with no duplicate and no conflict (Tasks 3, 4).
2. A full page of 1 000 rows whose `merge` is `[a, last − 1]` stores the row(s) at `last` and leaves the span ending at `last − 1`. `merge` at the exact boundaries `a = through + 1` (accepted) / `through + 2` (refused), `e = from − 1` / `from − 2`, an interval inside the span (no-op), and a refused `merge` rolls back the final chunk's rows (Task 3).
3. NULL vs price and price vs NULL are conflicts; Regular and Special of one `fundingTime` never conflict; the same observation twice is one conflict row (the unique index uses `COALESCE(mark_price, '')`) (Tasks 1, 2).
4. The signed check accepts `-0.0001`, `0`, `0.5` and refuses `-0`, `-`, `+1`, `--1`, `1.50`, `00.1`, `.5`, `5.`, `1e20` (a bound number is coerced to text, not refused: control test); it agrees with `canonical_decimal` on the corpus and differs from it only at the documented 97-digit boundary (Task 1).
5. No funding transaction begins while a candle write is active, also after a cancelled write; `SQLITE_BUSY` fails only the funding transaction and creates no conflict (Tasks 4, 5).

### Task 3: The span `merge` in the final transaction

**Files:**

- `@dataclass(frozen=True) SpanMerge(venue: str, symbol: str, interval: Interval, verified_at_ms: int)` (`Interval` from `domain/funding_rate_span.py`; `ensure_venue`, `ensure_symbol`, `ensure_timestamp_ms` for `verified_at_ms`, `type(interval) is Interval`).
- `FundingRateWriter.write_transaction(rows, *, ingested_at_ms, merge: SpanMerge | None = None)`. With `merge`: after the row inserts, in the same transaction, execute `_MERGE_INSERT`, `_MERGE_UPDATE` (the statements of ADR-0004 P-7 with `:v, :s` taken from `SpanMerge.venue` / `SpanMerge.symbol`) and `_SELECT_SPAN` (its text starts exactly with `SELECT from_ms`; `_SELECT_STORED` does not, so a fault prefix hits only one of them). Before the `merge` statements the transaction reads `span_before` with the same `SELECT`; if the span does not contain `[a, e]` → rollback and raise `FundingSpanNotAdjacentError` (no row of this call is kept, the connection stays usable). `rows` may be empty when `merge` is given.
- The series `(venue, symbol)` is part of `SpanMerge`, because an empty page has no rows. When `rows` is non-empty every row must belong to that series (`ValueError` before any SQL). The rows' times are deliberately **not** checked against `interval` (a full page's last row lies at `through_ms + 1`, see Decisions).
- `span_before` / `span_after` of the report: the span read inside the transaction before and after the `merge` statements; both `None` without a `merge`; `span_before` is `None` when the series had no span.

Semantics: `verified_at_ms` in the SQL is the `SpanMerge` field; `ingested_at_ms` stays the rows' column. The grown span is `min(from_ms, a)`, `max(through_ms, e)`; `verified_at_ms = max(old, new)`.
