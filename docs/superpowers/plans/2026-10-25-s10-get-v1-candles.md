# S10 API `GET /v1/candles` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `quasar-api serve --db PATH` serves `GET /v1/candles` exactly as `docs/contracts/api-v1.md` specifies: stored closed candles as exact decimal text, a clock-free `coverage` block, time-based pagination, one error body, and `503 not_ready` instead of an empty answer whenever the database cannot be read. After S10 the Collector writes and the API reads as two separate processes.

**Architecture:** Pure parts first: `api/errors.py` (the error envelope), `api/params.py` (raw query string → `CandlesRequest`) and `domain/span_coverage.py` (slot states and counts). `api/candle_reader.py` runs one explicit read transaction on a read-only connection (readiness check, series lookup, `limit + 1` candle read, conflict and unavailable reads) and assembles a `CandlesPage`. `api/database.py` opens a fresh read-only connection per request and maps every storage failure to the contract's `503`/`404`. `api/app.py` is a thin FastAPI app (app factory, no global state) that parses by hand so the contract's strictness (400 not 422, repeated/unknown/empty parameters) holds. `api/cli.py` gains `serve`.

**Tech Stack:** Python 3.12, stdlib `sqlite3`/`urllib.parse`/`re`/`os`; new runtime dependencies `fastapi` and `uvicorn`, new dev dependency `httpx` (Starlette `TestClient`) — see Decision 1; pytest, mypy strict, ruff, import-linter. No other new dependency (in particular no `pytest-timeout`: every wait in the tests is bounded by construction).

**Spec:** `docs/contracts/api-v1.md` (approved 2026-10-23; sections 1–5 are normative, 5.5 lists the required tests, 5.6 the implementation requirements), `docs/superpowers/specs/2026-10-20-market-data-v1-design.md` (S10 in §8, D5, D6, §11.5), `docs/adr/0002-sqlite-schema-v1.md` (C-3, C-5, C-6, P-5 to P-8), `docs/invariants.md` (INV-007, INV-009, INV-013, INV-014, INV-028). Earlier plans: S6 (`open_reader`, `verify_schema`), S8 (conflict records).

## Decisions made in this plan (open to review; 1, 2, 9 and 10 need user approval)

1. **New dependencies (needs approval).** `fastapi` and `uvicorn` (runtime; the stack in `CLAUDE.md` names FastAPI and spec D6 adds it "in the slice that first needs it"; a server is needed to run the process) and `httpx` (dev only; Starlette's `TestClient` requires it). No `fastapi[standard]`, no `uvloop`/`httptools`. Versions: whatever `uv add` resolves, lower bounds recorded in `pyproject.toml`, `uv.lock` committed (CI uses `UV_LOCKED=1`).
2. **`quasar-api serve` (needs approval).** New subcommand `serve --db PATH [--host 127.0.0.1] [--port 8000]`; default bind is localhost (contract §1, Exposure). `--db` need not exist: the API starts and answers `503 database_missing` (contract Q7). It is the only new CLI surface.
3. **Manual parsing, no declared FastAPI parameters.** The handler reads `request.scope["query_string"]` and parses it with `urllib.parse.parse_qsl(..., keep_blank_values=True, strict_parsing=False, errors="strict")` so repeated, unknown and empty parameters are visible and every error uses the contract body. `redirect_slashes=False`; `docs_url`, `redoc_url`, `openapi_url` are `None` (otherwise `/docs` would answer `200` where the contract says unknown paths are `404 not_found`). `HEAD` is not registered (FastAPI does not add it) so it is `405`.
4. **Undecodable query string (contract §1 says `%` and non-ASCII must be percent-encoded; it does not name the error shape).** `raw_query` (bytes) is first decoded with `.decode("ascii")`, so any raw byte `>= 0x80` fails (`parse_qsl` on bytes never decodes and ignores `errors="strict"`; a `latin-1` decode would silently accept mojibake). Then a malformed escape (regex `%(?![0-9A-Fa-f]{2})`, e.g. `a=%zz` or a trailing `%`) and a percent-escape that does not decode to valid UTF-8 (`parse_qsl` on the `str` raises `UnicodeDecodeError`) are rejected. Each is `400 invalid_parameter` with `details: {"received": <raw query cut to 64, decoded with "ascii" and errors="replace" so building the error cannot raise>}` and no `parameter` key (the name may be the undecodable part). `received` in every other `invalid_parameter` is the **decoded** value cut to 64 characters. `parse_qsl` decodes `+` as a space (an unencoded `+` in `symbol` is rejected as whitespace; `%2B` is a plus), `;` is an ordinary value character, and an empty pair (`a=1&&b=2`) is skipped by `parse_qsl`; that is accepted and tested. A pair without `=` (`start`) is an empty value → `400`. The reviewer confirmed the approach; no contract text changes.
5. **Error mapping for storage failures (revised by review 2).** There is **no filesystem check before the open**; the open is attempted first and a failed open is classified afterwards, so there is no check-then-open race.
   - *Open failed* (`sqlite3.Error` or `OSError` from the connection factory): classify the path with one `os.stat(db_path)`: `FileNotFoundError` or `NotADirectoryError` → `database_missing`; **any other `OSError` from `os.stat`** (`PermissionError`, `ELOOP`, `EIO`, …) → `database_unreadable`; the stat succeeds (the file exists but could not be opened, or it is a directory or another non-regular file) → `database_unreadable`. `Path.is_file()` is not used: it re-raises `PermissionError`, which would become a `500` for a condition the contract calls `503`.
   - *Race on classification:* the path may change between the failed open and the `os.stat`. The worst outcome is a wrong **reason** (`database_unreadable` instead of `database_missing`, or the reverse) on that one response, always as a `503` with the matching `Retry-After`; never a `200`, never an empty page, never a `500`. Both reasons ask the client to retry.
   - *Read failed:* `SchemaMismatchError`, and `sqlite3.DatabaseError` with `sqlite_errorcode == 26` (`SQLITE_NOTADB`, "not this project's") → `schema_mismatch`. `OSError` and every `StorageError` other than `SchemaMismatchError` (for example `UnsupportedSqliteError` from `open_reader`, which re-checks the version on each call) → `database_unreadable`. A `sqlite3.DatabaseError` is decided by its **error code** (review 3): the primary codes PERM, BUSY, LOCKED, NOMEM, INTERRUPT, IOERR, CORRUPT, FULL, CANTOPEN, PROTOCOL and the extended `READONLY_*` codes (recovery, cannot lock, directory, ...) → `database_unreadable`; `SQLITE_ERROR` (a bad statement), a plain `SQLITE_READONLY` (a write attempt) and every other code → a bug, propagated. An error built in Python (no `sqlite_errorcode`) keeps the class rule: `OperationalError` or an exact `DatabaseError` → `database_unreadable`.
   - *Everything else is a bug and propagates to `500`:* the codes above, `sqlite3.ProgrammingError`, `InterfaceError`, `NotSupportedError`, `DataError`, `IntegrityError`, `InternalError` (wrong bindings, a closed connection) and every non-`sqlite3` exception. The earlier wording "every other `sqlite3.Error` → `database_unreadable`" and the first draft of this decision (all `OperationalError` → `503`) are removed: they would have turned programming errors into `503` (contract: "`500` is reserved for bugs").
   - The unsupported-SQLite-version check happens once at `serve` startup, not per request.
6. **The slot classifier is pure and lives in `domain/span_coverage.py`.** S11 (coverage with `as_of`) will extend it; S10 needs exactly the clock-free subset of contract section 4. No new abstraction beyond one function and one result dataclass.
7. **One read-only connection per request**, opened and closed inside a worker thread (`starlette.concurrency.run_in_threadpool`), no pool, no shared state. The connection factory is injectable (`create_app(db_path, open_connection=open_reader)`) for fault injection only.
8. **`conflicted` flag = slot state `conflicted`** (a conflict record exists, or both a candle and an unavailable record exist), so the flagged candles are exactly the conflicted slots that have a stored candle (contract 5.3).
9. **Task 7 is split into two commits (review 2, finding 6; needs approval only as a plan-structure change).** Task 7 "Boundaries" (import-linter contract, AST scan, read-only tests; verifiable by `make check` alone, touches no document) and Task 8 "Invariant register and documentation" (register, README, the two contract sentences, optional live demonstration). Task 8 depends on Task 7 only through test names it cites as evidence; there is no dependency in the other direction and no circularity. Both commits pass `make check` on their own.
10. **INV-013 is not marked `ENFORCED` (review 2, finding 4; needs approval).** The invariant says handlers "never fetch exchange data". The tests can show less: (a) *static*: the `api` package imports no exchange library (INV-038) and none of `httpx`, `requests`, `aiohttp`, `websockets`, `socket`, `ssl` (import-linter), (b) *AST scan*: it also does not import `urllib.request`, `http.client`, `importlib`, `ctypes`, `subprocess`, does not call `__import__` or `asyncio` `open_connection`/`create_connection`, (c) *runtime guard, tested paths only*: the API test-suite requests open no outbound TCP connection (`socket.connect`, `connect_ex`, `create_connection` raise). Not covered: any transport reached through code outside the scanned names (a transitive dependency, `asyncio` streams reached by an alias, UDP `sendto`, a future module), and everything outside the request paths the tests exercise. Recommended: **INV-013 stays `PLANNED`** with an updated mechanism text and target S21 (Docker Compose: no outbound network for the API service), and a **new INV-044** states exactly the narrowed claim and is `ENFORCED`. The alternative (INV-013 → `ENFORCED` with the narrowed scope in its text) is possible but makes the headline sentence say more than the evidence shows; the user decides.

## Review Focus

Failure modes a reasonable user would expect handled, most likely first; each has a test in the owning task.

1. A client pages through a series with gaps and exactly-full pages and must always terminate with every stored candle seen once (Task 3, Task 5).
2. Integer lookalikes (`1_000`, `+5`, `-5`, ` 5`, `5` followed by `%0A`, Arabic-Indic, full-width and superscript digits, `1.0`, 17 digits) and repeated/unknown/empty parameters are `400`, never accepted or ignored (Task 1).
3. The database file is deleted, replaced by a foreign file or a newer schema while the API runs, or its path cannot even be inspected (permission denied) → the next request is `503` with the right `reason`, and the API recovers when the file is fixed; it never answers `200` with an empty list and never `500` for an environment problem (Task 4, Task 6).
4. The Collector commits while the API reads, and after the Collector has closed (WAL checkpointed, `-wal`/`-shm` removed) → the API reads committed data from one snapshot and still opens the database read-only (Task 3, Task 4, Task 6). A read-only open of a WAL database recreates the `-wal`/`-shm` sidecars in a writable directory; the main database file is never changed.
5. A storage error message, SQL text or file path never reaches a response body; a non-ASCII symbol round-trips in UTF-8 (Task 5).
6. A programming error (wrong bindings, closed connection) is a `500`, never a `503` that would hide it (Task 4, Task 5).
