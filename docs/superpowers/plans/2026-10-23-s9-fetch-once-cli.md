# S9 Collector `fetch-once` CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `quasar-collector fetch-once --db PATH --symbol SYMBOL` fetches the most recent 5m klines of one Binance USDT-M perpetual, keeps only candles that are confirmed closed under ADR-0001, and stores them idempotently; anything untrusted, malformed, conflicting or of unknown persistence outcome is reported and never hidden.

**Architecture:** A use case `collector/fetch_once.py` orchestrates existing parts (server-time observation → `server_lower_bound` → raw klines → `parse_klines` → `select_closed_candles` → `AsyncCandleWriter.write(selection.eligible)`) against two injected seams: a `KlineSource` protocol and a `Clock` protocol. `collector/binance_usdm.py` is the only module that imports CCXT (async client, implicit raw endpoints, ADR-0001 D-A/P-1), enforced by an import-linter contract. `collector/cli.py` adds the subcommand, migrates the database on startup (the Collector's job, S6/S7) and maps outcomes to exit codes. Before any of that, Task 1 makes the existing writer report precisely whether a failed batch is certainly not stored or of unknown outcome, because the CLI must not claim more than the writer can prove. Unit tests use fakes and the committed fixtures; the one live test is marked `live` and excluded from `make check`.

**Tech Stack:** Python 3.12, `ccxt` (async client, new runtime dependency), stdlib `asyncio`, `argparse`, `urllib.parse`, `contextlib`, `sqlite3`; pytest, mypy strict, ruff, import-linter.

## What was verified about the existing writer (2026-10-23)

- `CandleWriter.write` runs one `BEGIN IMMEDIATE … COMMIT` per batch; a statement failure triggers `ROLLBACK`; a rollback that raises or leaves the transaction open makes the writer unusable. `AsyncCandleWriter` runs the same code on one worker thread and passes exceptions through unchanged; a cancelled caller cannot know whether its batch was applied (documented in S7).
- **Real SQLite (3.54.0) probe:** a `COMMIT` that fails for real (deferred foreign-key violation on a temp table) raises `sqlite3.IntegrityError`, leaves `in_transaction` true, and a following `ROLLBACK` leaves zero rows. A failed `COMMIT` whose transaction is *no longer open* (for example after an I/O error during sync) is a different case: SQLite may already have written the commit record, so the batch may be stored.
- **Defect found:** the S7 writer raises `CandleWriteError("batch failed and nothing was written: …")` for every `sqlite3.Error`, including a `COMMIT` error after which the connection is no longer in a transaction. In that case "nothing was written" is not proven. S7's injected faults raise *instead of* executing `COMMIT`, so they could never show this. INV-030 in the register overclaims accordingly; Task 1 and Task 6 correct both.
- The batch itself is atomic (all or none); the only uncertainty is *which*, never a partial batch. Re-sending is always safe (INV-029).
- **Cancellation (read from `async_candle_writer.py`):** `write` is `await loop.run_in_executor(self._executor, job)` on a one-thread FIFO executor. Cancelling the caller cancels the executor job only if it has not started; a job that is running continues to commit or roll back and its result is discarded, a job still queued is withdrawn on a best-effort basis. So after a cancelled `write` the outcome is unknown by design (documented in S7).
- **`close()` (read from the code):** `close()` sets `CLOSING`, starts one shared `_do_close` task and awaits it through `asyncio.shield`; `_do_close` submits `CandleWriter.close` to the *same* FIFO executor, so it runs after every write that was accepted earlier and can neither overtake nor race an in-flight write. A failure of that job is re-raised as a **plain** `CandleWriteError("closing the connection failed: …")`; the executor is shut down and the state is `CLOSED` in a `finally` either way. Therefore (i) a plain `CandleWriteError` from `close()` says nothing about any batch and must never be mapped like a write error, and (ii) when `close()` returns or raises, every accepted write has finished executing, but a *cancelled* caller still does not learn how that write ended.
- **`ROLLBACK` before `COMMIT` (read from `candle_writer.py`):** `_roll_back` marks the writer unusable when the rollback raises or the transaction survives. In that case `COMMIT` was never issued, so the batch cannot have become durable (an uncommitted transaction has no commit record; SQLite ignores such WAL frames on recovery). What is unknown is the *state of the connection*: its transaction may still be open and hold the write lock until the connection is closed. These are two different facts and the messages must keep them apart.

## Decisions made in this plan

1. **Eligibility is judged at the instant the klines request is sent, not after the response.** The data is a snapshot taken after the request arrives, so server time at the snapshot is at least the lower bound at send time. A bound taken after a slow response would confirm a candle the server had not yet settled when the snapshot was taken (ADR-0001 P-6: values change up to ~8 s after close). Server time is observed first, and `server_lower_bound` is evaluated with the readings taken immediately before `fetch_klines`.
2. **The klines are fetched even when time is untrusted.** `select_closed_candles` is then the single gate (all candles become pending, reason reported), and the INV-007 proof exercises the real gate on both the forming candle and the untrusted case. Cost: one extra request in a degraded state.
3. **Async CCXT (`ccxt.async_support.binanceusdm`)**, matching the asyncio architecture and `AsyncCandleWriter`. The S2 spike used the synchronous client; the async client's raw payload (strings preserved) is **not yet verified** and is first checked by the live test (Task 5). Raw implicit endpoints only: `fapiPublicGetKlines`, `fapiPublicGetTime`. Unified `fetch_ohlcv` is never used.
4. **Fail closed at the adapter.** Only a market whose CCXT record shows `swap`, `linear`, `settle == USDT`, `quote == USDT`, no `expiry` is accepted (ADR-0001 P-9); only timeframe `5m` (the only one ADR-0001 measured); the `fapiPublic` base URL must pass a strict parsed check (Task 3) **before** any request, including `load_markets`.
5. **No new configuration mechanism.** CLI flags only (`--db`, `--symbol`, `--limit`, `--publication-delay-ms`); defaults are the ADR-0001 values. `--db`'s parent directory must exist; the CLI never creates directories.
6. **CLI contract (new, needs approval).** Exit `0`: every eligible candle stored, nothing invalid or conflicting. Exit `3`: eligible candles stored, but the run found invalid candles or recorded conflicts. Exit `1`: failure after which **nothing was written, with certainty** (directory or schema or migration error, source error, malformed batch, untrusted time, a write error the writer reports as not applied). Exit `4`: the write's **outcome is unknown** (`CandleWriteOutcomeUnknown`); the batch is stored fully or not at all and re-running reconciles it. Exit `130`: interrupted; whether the last batch was stored is **unknown** (see decision 10). Exit `2`: argparse usage error. Pending candles alone (the forming candle) are normal and exit `0`. stdout is plain `key=value` lines printed only once a complete report exists; messages go to stderr; no message claims "nothing stored" unless the exit code is `1`.
7. **Writer outcome semantics (Task 1).** Two facts are reported separately: *persistence* (is the batch durably stored?) and *connection state* (is the transaction closed, is the write lock released?). `CandleWriteOutcomeUnknown(CandleWriteError)` is raised exactly when `COMMIT` was issued and failed *and* either the transaction is no longer open or the rollback could not be confirmed. A failure before `COMMIT` is always a plain `CandleWriteError` meaning "not committed", also when the `ROLLBACK` then fails: the writer becomes unusable and the message says the rollback is unconfirmed and that the connection may hold the write lock until it is closed; it does not say "rolled back". A failed `COMMIT` with the transaction still open that is then rolled back is also a plain `CandleWriteError`. The type passes through `AsyncCandleWriter` unchanged.
8. **Architecture guarantee, stated precisely.** The contract `ccxt is imported only by the Binance adapter` forbids *static imports* of `ccxt` from every module of `api` and `collector` except `collector/binance_usdm.py` (via `ignore_imports` on that single edge); `domain` and `storage` are covered by their existing contracts. It does not cover dynamic imports, other HTTP clients, `tests/` or `spikes/`, so INV-013 (API handlers never fetch exchange data) stays PLANNED for S10.
9. **Closing failures are warnings only when persistence is settled.** Persistence is settled when the run ended with a complete `FetchOnceReport`, or with an error that proves no write was attempted or that the attempted write was not committed (`SourceError`, `KlineParseError`, a plain `CandleWriteError` from `write`, any initialization failure). Then a resource that fails to close is reported on stderr as `warning: closing <name> failed: <message>`; it never changes the exit code and never skips the remaining closes. When the run ended with `CandleWriteOutcomeUnknown`, `KeyboardInterrupt` or cancellation, persistence is *not* settled: the exit status stays `4`/`130` whatever `close` does, a failing close only adds a warning line, and a successful close is not evidence of anything. A plain `CandleWriteError` raised by `AsyncCandleWriter.close()` is classified by where it came from (the close wrapper), never by its type.
10. **Interruption.** `asyncio.run` turns the first `SIGINT` into a cancellation of the main task and, after the coroutine has unwound, a `KeyboardInterrupt` from `run`; a `KeyboardInterrupt` raised inside the coroutine unwinds the same way. During the unwinding the pushed `writer.close()` is awaited; because it is queued behind any in-flight write on the single FIFO worker and is shielded from cancellation, shutdown cannot overtake or race that write, and `main` returns only after the write job has finished (commit or rollback). The cancelled caller never receives the write's result, so the outcome is **unknown**: exit `130`, stderr `interrupted: whether the last batch was stored is unknown; re-run the same command to reconcile (writes are idempotent)`, nothing is printed on stdout. A second `SIGINT` during shutdown is not handled specially: the worker thread still completes its transaction or the process dies, SQLite keeps the file consistent, and the next run reconciles. An interrupt that arrives after the report was printed still exits `130` with the unknown message, which under-claims and is accepted.

## Review Focus

Failure modes a reasonable user would expect handled, most likely first. Each has a test in the owning task.

1. The exchange returns the still-forming candle as the last row → never stored (Task 2, end to end on `btcusdt_5m_forming_raw.json`).
2. Server time cannot be trusted (request failed, round trip too slow) → nothing stored, exit 1, reason shown (Tasks 2, 4).
3. A candle becomes eligible only while a slow klines request is in flight → stays pending (Task 2).
4. A malformed row or a JSON number in a text slot → the whole batch is rejected, nothing stored, exit 1 (Tasks 2, 4).
5. `COMMIT` reports an error although it took effect → exit 4 with an "unknown outcome" message, never "nothing was stored"; re-running reconciles with no duplicates (Tasks 1, 4).
6. The command is run twice, or after a restart, or a settled value was revised → duplicates change nothing; a revision is recorded and exits 3 (Tasks 2, 4).
7. A symbol that is unknown, COIN-M, delivery or not USDT-quoted, or a CCXT endpoint that is not exactly `https://fapi.binance.com/fapi/v1` (look-alike hosts, `userinfo@` tricks, other ports or paths) → refused before any request (Task 3).
8. Any initialization or runtime failure, or a failing `close`, leaves a connection, exchange client or writer open, or skips the other closes (Task 4).

Semantics of `write`. Track whether `COMMIT` has been issued. (a) An `sqlite3.Error` before `COMMIT` is issued and the rollback is confirmed (connection out of the transaction): plain `CandleWriteError`, message "batch rolled back; nothing was written". (a') The same, but the `ROLLBACK` raises or leaves the transaction open: the writer is marked unusable as today and the error is still a plain `CandleWriteError`, because no `COMMIT` was ever issued and an uncommitted transaction cannot become durable; but the message says "batch not committed; rollback could not be confirmed; this connection is unusable and may hold the write lock until it is closed" and does **not** say "rolled back". Persistence (certainly not stored) and connection state (unconfirmed) are reported as separate facts. (b) `COMMIT` raises `sqlite3.Error` and `conn.in_transaction` is still true: `ROLLBACK`; if the connection is then out of the transaction, plain `CandleWriteError` ("COMMIT failed and was rolled back; nothing was written"). (c) `COMMIT` raises and the connection is not in a transaction, or the rollback in (b) fails or leaves the transaction open (writer marked unusable as today): raise `CandleWriteOutcomeUnknown` with a message that says the outcome is unknown, that the batch is atomic, that re-sending is safe, and does **not** contain "nothing was written". The writer stays usable in the "not in a transaction" case. Non-`sqlite3` exceptions behave as in S7.

Semantics of `fetch_once`, in this order. (1) Read `clock.monotonic_ns()`, `await source.fetch_server_time_ms()`, `clock.monotonic_ns()`, `clock.wall_ms()` and build a `ServerTimeObservation`; a `SourceError` here means no observation (`None`), not a failed run. (2) Immediately before the klines request read `clock.monotonic_ns()` and `clock.wall_ms()` and compute `time = server_lower_bound(observation, those, None, config.time_trust)`. (3) `await source.fetch_klines(config.symbol, config.timeframe, config.limit)`; a `SourceError` propagates. (4) `parse_klines(rows, config.symbol, config.timeframe)`; `KlineParseError` propagates, nothing is written. (5) `select_closed_candles(candles, config.publication_delay_ms, time)`. (6) If `selection.eligible` is non-empty, `await writer.write(selection.eligible, ingested_at_ms=clock.wall_ms())`, else no write call; any exception from the writer, including `CandleWriteOutcomeUnknown`, propagates unchanged. Return the report. Nothing else may reach the writer.

## Risks and boundaries

- **Contract:** `quasar-collector` gains one subcommand; `--version` and bare invocation keep their behavior.
- **Data integrity:** the 15 s publication delay is a margin over 13 observed boundaries on one instrument, not a proven bound (ADR-0001 P-3); S8 records any later revision as a conflict. Eligible candles are written even when the same run reports invalid ones (exit 3), which is deliberate: valid data is not held hostage to one bad row. The "unknown outcome" branch is proven only with an injected fault (a real I/O failure during `COMMIT` cannot be produced portably); the "certain" branch is proven with a real SQLite `COMMIT` failure.
- **Interruption:** a second `SIGINT` while the shutdown is still waiting for an in-flight write is not handled; the worker thread finishes its transaction or the process dies, and SQLite's atomic commit keeps the file consistent, but the run's own outcome is unknown and the next run reconciles. Exit `130` after the report was already printed under-claims (the report is final). The real-signal test depends on being in the main thread with the default `SIGINT` handler and is skipped otherwise.
- **Operational:** one run is one process with one time observation; there is no retry loop, backoff or rate-limit policy beyond CCXT's own (S13/S14). Binance reachability from the build machine is unchecked until Task 5.
- **Security:** public endpoints only; no credentials, no trading. The URL check also blocks a misconfigured or hijacked CCXT base URL from receiving requests.
- **Scope check:** the spec asks that slices combining independent responsibilities are split during planning. S9 combines a writer correction (Task 1), a use case (Task 2), an adapter (Task 3) and a CLI (Task 4). The plan can be executed as two reviews: Tasks 1–2, then Tasks 3–6. Tasks 1 and 2 are independently valuable (the first corrects a claim, the second proves INV-007 offline).
